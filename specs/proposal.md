# 智能日报生成器

## 1. 背景与目标

### 1.1 背景
目前，团队成员每天需要耗费 15~30min 手动撰写日报，内容涵盖当日代码提交、任务进展及协作沟通情况。这一过程不仅重复低效，且常因遗忘导致信息缺失。

另外，团队 Leader 需要掌握成员的工作动态，但人工撰写的日报往往信息密度低、格式参差不齐，严重影响了阅读体验与管理效率。

### 1.2 目标
构建一个自动化工具，旨在从团队现有的协作平台中抓取当日工作数据，自动生成结构化日报，并精准推送给相关干系人。

### 1.3 目标用户
- 主要用户（数据生产者）：5~15 人的研发团队核心成员
- 主要读者（数据消费者）：团队 Leader 及项目经理

## 2. 功能范围

### 2.1 做什么（本期）

#### 数据采集
- 对接 GitHub/GitLab，获取当日代码提交记录（含 Commit Message 及变更统计）
- 对接飞书/Jira，抓取当日任务状态流转（如新建、进行中、已完成）
- 从飞书群消息中提取与项目强相关的讨论摘要
- 采集飞书考勤数据（新增 v1.1）：获取成员当日签到、签退与工时

#### 日报生成
- 将采集数据按“代码提交 → 任务进展 → 协作沟通”的逻辑进行三段式编排
- 为每位团队成员生成独立的日报段落
- 输出 Markdown 格式（支持无缝转换为 HTML 邮件）

#### 推送通知
- 每个工作日 18:00 自动触发日报生成流程
- 通过 SMTP 服务向团队 Leader 发送 HTML 格式日报
- 通过飞书机器人将 Markdown 格式日报推送至团队群组

### 2.2 不做什么（本期明确排除）
- 不做智能摘要和 AI 总结（本期仅做数据清洗与整理，不涉及语义理解）
- 不做移动端
- 不做历史日报的搜索与统计图表分析
- 不做个人日报的手动编辑与补充功能
- 不做支持多团队隔离 / 多租户架构

### 2.3 技术约束
- 开发语言：Python 3.11 及更高版本（复用团队现有技术栈）
- 部署环境：公司内网服务器（Docker 容器化部署）
- 外部依赖：GitHub API、飞书开放平台 API、公司邮件服务（SMTP）
- 运行方式：基于 Cron 的定时任务，不需要常驻后台服务
- 数据存储：本地 SQLite（仅用于存储日报历史记录，不需要部署远程数据库）

## 3. 验收标准

### 3.1 功能验收
- [ ] 能够准确获取指定 GitHub 仓库过去 24h 内所有成员的 Commit 记录
- [ ] 能够准确获取飞书项目中当日发生状态变更的任务列表
- [ ] 能够从飞书群消息中筛选并提取包含指定关键词的讨论记录
- [ ] 生成的日报必须包含“代码提交”“任务进展”“协作沟通”三个核心板块
- [ ] 日报 Markdown 格式规范，可直接渲染为高可读性的 HTML 页面
- [ ] 邮件发送链路畅通，团队 Leader 能成功接收到 HTML 格式日报
- [ ] 飞书机器人能够成功将日报推送至指定群组

### 3.2 性能验收
- [ ] 单次日报生成耗时（以 5 人团队为例）<60s
- [ ] 单一数据源（如某 API）超时或失败，不应阻断其他数据源的采集
- [ ] 采集失败的数据源需要在日报中显式标注“数据获取失败”，严禁静默跳过

### 3.3 边界场景
- [ ] 若团队成员当日无任何提交、任务或消息，日报对应板块应显示“今日无记录”
- [ ] 当 GitHub API 触发限流时，系统应具备等待并重试机制（上限三次）
- [ ] 当飞书 Token 过期时，系统应能自动刷新 Token
- [ ] 系统需要识别非工作日（周末及法定节假日），并自动跳过日报生成

### 3.4 v1.1 新增验收
- [ ] 日报中包含每位成员的当日工时和出勤状态
- [ ] 考勤数据不可用时，日报对应字段应明确标注“考勤数据暂不可用”

## 4. 术语定义
| 术语 | 定义 |
|---|---|
| 日报 | 系统自动生成的每日工作摘要，涵盖代码、任务、沟通三个维度 |
| 成员 | 已在系统中完成 GitHub 与飞书账号映射绑定的团队成员 |
| 数据源 | 提供原始工作数据的外部协作平台（GitHub、飞书任务、飞书消息、飞书考勤） |
| 采集窗口 | 单次采集所覆盖的时间跨度，默认为当日 00:00 至任务执行时刻 |
